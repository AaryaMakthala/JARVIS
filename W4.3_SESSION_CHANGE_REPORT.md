## 2. Defects found in the partial implementation

1. **`contacts.py` — malformed and incompatible `resolve()`.** The previous session had
   replaced the W4.2 signature with `resolve(query, *, prefer_number=None) -> list[ContactMatch]`
   followed by **ten identical stacked docstrings**. Problems: `ContactMatch` does not exist
   anywhere in the repository (the annotation was only inert because of
   `from __future__ import annotations`); `prefer_number` was never used; and the new docstring
   claimed a *unique-only / empty-on-ambiguity* contract while the body still returns every
   exact key hit and then substring matches — which the CLI describe paths and
   `test_whatsapp.py` (`resolve("ra") == ["Rahul", "Sara"]`) depend on. No caller expected a
   `ContactMatch`, and nothing needed `prefer_number`. **Reverted to the exact W4.2 method**
   rather than inventing a new type; there is no compatibility problem because no caller wanted
   the changed shape.
2. **`tools/whatsapp.py` — `NameError` on every desktop send.** The import of
   `WhatsAppDesktopAdapter` had been deleted while `_whatsapp_send_run` still constructs it.
   Restored. The `CONTACT_GROUNDABLE_TOOLS` re-export was kept (added to `__all__`) but the
   self-referential `CONTACT_GROUNDABLE_TOOLS: frozenset[str] = CONTACT_GROUNDABLE_TOOLS`
   assignment was removed.
3. **Grounding refused informative precheck failures.** `ground_brain_update` builds
   `ContactStore(config.contacts_file())`; the precheck tests inject a store into the tool spec
   only, so grounding resolved every recipient against an empty real file and halted before the
   precheck ran. Tests now configure the injected store as the configured file as well, which is
   what production has.
4. **One refusal message for three different failures.** `"I couldn't identify that contact from
   your saved contacts."` covered no-match, model uncertainty and malformed output alike.
   Split: `NONE` -> no-match; `UNCERTAIN`/out-of-range/name/number/malformed/model error ->
   invalid grounding; ambiguity -> a clarification question naming the candidates.
5. **Four recipient-precheck assertions had been rewritten to a string the code never produced**
   (the precheck emits `no contact matches …` / `multiple contacts match …`). The underlying
   failures were defect 3, not wording; the assertions were corrected to the real behaviour
   rather than the production text being bent to a guessed string.

## 3. Final behaviour

```
user request -> brain (one structured decision)
             -> project plan
             -> ground_brain_update            <-- W4.3, before everything below
                  deterministic resolve_contact   (no model call on a hit)
                  | ambiguous -> clarification interrupt naming candidates
                  | unresolved -> tool-free llm.text over C<n> ids
                       C<n> -> re-resolve in ContactStore + same-key check
                       NONE -> no-match refusal
                       else -> invalid-grounding refusal
             -> validate -> policy_gate (precheck backstop) -> Tier 2 confirm
             -> action hash over tool + canonical args -> act -> tool
```

Grounding mutates only the step's `contact` argument. Message text, paths, tiers, confirmation
payload and the action hash are untouched by the model.

## 4. Security properties

| Requirement | Result |
|---|---|
| Deterministic match before any LLM call | yes — `_deterministic` runs first, `_NeverCalledLLM` proves it |
| LLM only sees candidate ids + saved display names | yes |
| No phone numbers / cookies / message bodies / auth material in the grounding prompt | yes (test asserts the digits are absent) |
| Tool-free model call | yes — plain `llm.text`, no schema, no tools, `max_tokens=16` |
| Model can only return an in-set id | yes — strict `^C([1-9][0-9]*)$`, range-checked |
| Invented name / number / out-of-range id refused | yes |
| Chosen candidate re-resolved from ContactStore | yes — fresh read, must still be `exact` |
| Indistinguishable candidates stay ambiguous | yes — same `normalize_name` key => clarification |
| LLM cannot authorize or lower a tier | yes — policy engine unchanged |
| Recipient bound before confirmation and action hash | yes — graph test compares `action_hash` against the canonical args |
| No post-confirmation recipient change | yes — act re-runs the precheck and re-checks the hash |
| W2 identity verification / W4 Tier 2 preserved | yes — suites unchanged and green |

## 6. Limitations

- Live provider behaviour for paraphrases ("my mother", "my best friend") is unmeasured; only
  scripted fakes were used.
- The candidate list is capped at 100 saved contacts; the model sees every saved display name.
- With two same-key contacts (`Mom ❤️` / `Mom 💙`) grounding always asks, even if a real model
  would pick one consistently.
- Desktop `whatsapp_send` is now in the groundable set, but its live DOM path remains unverified
  from W4.
- Ambiguity becomes a clarification round, so it consumes the bounded clarification budget
  (`MAX_CLARIFICATIONS`) rather than failing immediately.

- **LLM routing (B2)**: deterministic task-class classifier (`conversation` -> fast; `action`, `reasoning`, `coding`, `summarization`, `tool_args`, `local_ocr` -> planner), persisted route/reason metadata, closed date/time lookups, and a bounded arithmetic fast path. ## Local OCR migration (2026-11-10, complete)

- **Engine**: `src/jarvis/perception/ocr.py` now wraps PaddleOCR 3.7 with the exact PP-OCRv6 small models (`PP-OCRv6_small_det`, `PP-OCRv6_small_rec`). It uses `engine="paddle"`, `device="cpu"`, explicit `text_detection_model_dir`/`text_recognition_model_dir`, and sets `PADDLE_PDX_DISABLE_MODEL_SOURCE_CHECK=True` before import so a missing model is an honest error, never a download. No cloud vision, Tesseract, EasyOCR or runtime network fallback exists.
- **Model location**: models come from `[perception] ocr_model_dir` or `<JARVIS data dir>/models/paddleocr`. `jarvis doctor` reports PaddleOCR importability and whether both inference directories are present. Install instructions and the `paddlepaddle==3.2.0` pin (3.3.1's oneDNN CPU path crashes the 3.7 default pipeline) are in `docs/09_SETUP_AND_DEPENDENCIES.md`; research/licence notes are in `docs/12_DEPENDENCY_VERIFICATION.md`.
- **Bounds and lifecycle**: the adapter enforces `ocr_max_image_bytes` (16 MiB) and `ocr_max_image_side` (4096, downscaled with Pillow), accepts BGR numpy input, parses only `rec_texts`/`rec_scores`/`rec_boxes`, clamps and averages confidence, serialises inference with a lock, caches one lazily built engine per model configuration, and unloads it after `ocr_idle_unload_seconds` (300). Text/boxes/confidence are the entire capability; there is no general image understanding.
- **Privacy**: image bytes, base64, screenshot paths and OCR text are never written to task events, checkpoints, memory or logs, and never sent to an LLM. `read_screen`/`describe_screen` output stays tainted/untrusted and cannot authorize a consequential action. All cloud-vision settings and prompts were removed from `screen.py`, `ScreenSettings` and the default TOML; the invariant test now asserts no vision call path.

- **W3.1 read receipts**: NOT verified. The read path opens the chat through W2's number search and performs no explicit receipt action; whether WhatsApp marks messages read merely by opening the chat cannot be determined without a live account. Do not claim receipts are suppressed.
- **W5 status verification**: unit-verified only. The status vocabulary is WhatsApp Web's `data-icon`/aria-label set, read from the message meta node and **not** confirmed against a live account; a different or localised rendering yields `unknown` rather than a guess. Read receipts are a recipient privacy setting: when they are disabled the double check never turns blue, so `read` stays unobservable and the tool honestly reports `sent`/`delivered`/`unknown`. A body sent twice under two approvals is indistinguishable in one window and yields `unknown`. Verification navigates through the W2 route, which may itself mark messages read - navigation is not side-effect-free. Ledger retention is 7 days; older dispatches report "no record".
- **W4.4 guard retention**: protection is bounded by `RESEND_WINDOW_S` (600 s). A claim recorded by a crashed or uncertain process blocks replays inside that window and is pruned afterwards, so a manually reconstructed approval older than the window (same task id and action hash) is not blocked forever. The guard is a duplicate-send control, not an authorization ledger: the Tier-2 approval and the action hash remain the security boundary. Cross-process atomicity is verified on this Windows machine only; it relies on SQLite file locking over a local filesystem, so a guard file on a network share is not covered.
- **W4.3 contact grounding**: unit-verified only. Live model phrasing ("my mother", "my best friend") is unverified: the prompt caps the candidate list at 100 saved contacts and the model sees every saved display name (never a number). With two contacts sharing an emoji-insensitive key, grounding refuses even if the model picks one. An unknown literal name may be interpreted by the model, but the Tier-2 confirmation always shows the canonical saved name, so nothing is sent to an unapproved contact; whether a real provider reliably answers `NONE` for an unrelated name is unmeasured.
- **W6 incoming awareness**: unit-verified only. Unread discovery reads the visible `#pane-side` list through a read-only script; the unread-badge, preview and timestamp selectors are conservative fallbacks and have **not** been checked against a live WhatsApp DOM. Discovery reports only what the row exposes: a missing unread count, preview, timestamp or direction is reported as unavailable, never inferred. Conversation display names are untrusted labels and are matched to saved contacts only for labelling (`trusted`/`ambiguous`/`unverified`); they never prove identity for sending. Full conversation reading still opens the chat through the W2 number-search route, so it **can** mark messages read; the Tier-1 confirmation and result now say so, but whether WhatsApp actually changes receipts merely by opening the chat remains unverified and is never claimed. No background polling, replies, attachments or body persistence were added; incoming text stays tainted and untrusted.

Message text reaches only the dedicated tool-free summarizer, is persisted nowhere, and never enters a planner prompt directly; the summarizer pipeline itself is tool-free. One gap found and fixed: when a later step fails, the replanner previously received prior tool output raw. - **W5 (2026-11-02)**: read-only delivery/read-status verification for a previously dispatched WhatsApp text message. `MessageStatus` (`unknown`/`dispatched`/`sent`/`delivered`/`read`) is derived **only** from WhatsApp's visible status node: the page script now reports the bounded `data-icon` names and accessible labels found inside a message's meta node (max 8 hints, 80 chars each), and `jarvis.messaging.verification` maps only the documented vocabulary (`msg-check`/"Sent", `msg-dblcheck`/"Delivered", `msg-dblcheck-ack`/"Read", `msg-time`/"Pending"). Nothing else maps, two different indicators on one message are `unknown`, and a message merely appearing in the sender's chat is never delivery evidence - a Send click alone stays `dispatched`. The target is bound to the original operation through a new privacy-preserving SQLite ledger (`whatsapp_dispatches.sqlite3`): the W4 text adapter records `sha256(task_id:action_hash)`, the saved contact name, `sha256` of the whitespace-collapsed text, the dispatch time and `pending`/`dispatched`/`unknown` **before** the click; no body and no phone number are stored, retention is 7 days, and a ledger write failure is logged rather than failing an already-completed send. `whatsapp_verify_message` (Tier 1, contact-grounded, recipient precheck) resolves the contact through ContactStore, opens the chat through the existing W2 number-search route, reads one bounded window (20 messages), requires exactly one **outgoing** message whose digest matches and which has a readable timestamp, and relies on the driver's header verification before and after the read (a conversation switch is refused). Identical duplicate bodies are ambiguous -> `unknown`; an incoming message is never the target; missing direction/timestamp/content -> `unknown`. Optional bounded polling (`wait_seconds` 0..30, 2 s interval, no re-navigation, stops at the requested status) supports sent->delivered->read advancement. The operation is strictly read-only: no Send/click, no composer, no reply/forward/react/edit/delete, no attachment, no URL, no generic DOM or JavaScript, and an `unknown` result never triggers a resend. Coverage: `tests/unit/test_whatsapp_verify_message.py` (66 tests) plus the W4 send/read/contact-search/send-file/act suites. Live WhatsApp DOM and live delivery/read evidence remain **unverified**.
- **W6 (2026-11-02)**: incoming awareness. `whatsapp_list_unread` (Tier 0, read-only) scans only the visible conversation list (`#pane-side`, fallback `document.body`) through one bounded script and **never** opens a chat, so it cannot change read receipts. It validates `limit` 1..20, requires an authenticated session, refuses a foreign origin before probing, filters unread rows only, caps the result at 20, and bounds names (120), previews (160) and timestamps (40). Missing count/preview/timestamp/direction is reported as unavailable, not inferred. Display names are untrusted labels matched to the ContactStore only for `trusted`/`ambiguous`/`unverified` labelling; they never prove identity for sending. The existing `whatsapp_read_messages` (Tier 1) now labels outgoing messages `you`, incoming messages with the sender (or `incoming (sender unknown)`), and truly unavailable direction as `unknown sender (direction unavailable)`, counts incoming/outgoing/unknown, and discloses in its confirmation and output that opening an unread conversation can mark it read and that JARVIS cannot suppress or undo that. A dedicated constant carries the note into `data["read_receipt_note"]`. Both tools are registered (`whatsapp_list_unread` in the `messaging` group); message text remains tainted, is never persisted and is never obeyed by the tool-free summarizer. Coverage: `tests/unit/test_whatsapp_incoming.py` (70 tests) plus the W5/W3/contact-search suites. Live WhatsApp DOM, unread badges and read-receipt behaviour remain **unverified**.
- **W4.4 (2026-11-02)**: cross-process duplicate-send protection. The W4 guard was a JSON file written with `tmp.replace()` and serialised only by a process-local `threading.Lock`, so two JARVIS processes could both read "not claimed yet" and both claim the same approval. `FileSendGuard` now stores claims in a small SQLite database (`user_data_dir("whatsapp_text_sent.sqlite3")` for text, `whatsapp_sent_files.sqlite3` for attachments) with `key TEXT PRIMARY KEY, claimed_at REAL`: `claim()` runs `BEGIN IMMEDIATE`, prunes rows older than `RESEND_WINDOW_S`, then `INSERT OR IGNORE`, and only `rowcount == 1` is a win. SQLite's write lock is the cross-process authority - no Python lock is involved - and the wait is bounded by `GUARD_BUSY_TIMEOUT_S = 2.0`, so a contended claim refuses instead of hanging. The claim commits **before** the click, so a process killed after claiming leaves the row behind and that approval cannot be replayed; an unknown click outcome is equally non-retryable while the row is inside the window. `operation_guard_key`/`guard_key` and the `task_id:action_hash` operation identity are unchanged, so a newly authorized task with identical text claims a different key and sends. Every storage failure (corrupt file, a directory in the way, busy timeout, failed write) raises `GuardStorageError(OSError)`, which both adapters' existing `except OSError` already turns into a refusal, so a broken guard can never be read as "nothing was sent yet". Only opaque sha256 keys and timestamps are stored - never message text, paths or numbers.
